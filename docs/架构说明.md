# 架构说明

这份文档解释**为什么代码是这样组织的**。玩法数值见 [数值与平衡.md](数值与平衡.md)，
上手步骤见 [上手指南.md](上手指南.md)。

---

## 一、分层的唯一理由：让玩法能被验证

```
        ┌───────────────────────────────────────────────┐
        │  Unity 表现层   Assets/Scripts/Unity           │
        │  职责：把状态画出来 / 把手指变成指令 / 把事件变成音画  │
        │  依赖：UnityEngine、uGUI                       │
        └──────────────┬────────────────▲───────────────┘
         指令（方法调用）│                │ 事件（SimEvent 列表）
                        ▼                │
        ┌───────────────────────────────────────────────┐
        │  纯逻辑层   Assets/Scripts/Core                │
        │  职责：全部玩法规则                            │
        │  依赖：无（连 JsonUtility 都不用，自带 MiniJson）│
        └───────────────────────────────────────────────┘
```

Core 层的文件里**没有一行 `using UnityEngine`**。这不是洁癖，它换来三件具体的事：

1. **玩法可以在没有 Unity 的机器上编译和测试。**
   `tools/CoreTests` 用 .NET SDK 直接引用 `Assets/Scripts/Core/*.cs`，
   跑 146 项断言（JSON 往返、存档、成就、寻路、确定性、以及脚本机器人试打三个难度）。
2. **确定性可复现。** 模拟层用自带的 xorshift32（`SimRandom.cs`），
   同一 seed 必然同一局；战报会记下 seed，报错可以照着重放。
   （表现层的 `UnityEngine.Random` 只用来决定特效往哪飘，不影响胜负。）
3. **规则可以被穷举。** 成就、结算、平衡测试都只读 Core 的数据结构，不碰任何 GameObject。

### 代价

- 所有跨层数据必须是普通 C# 类型 → 于是有了 `Float2` / `GridPos`（而不是直接用 `Vector2`）。
- 跨层通信要显式协议 → 于是有了 `SimEvent` 结构体列表。
- 表现层要自己把格子坐标换算成 uGUI 坐标（`BoardView.CellToLocal` / `LocalToCell`）。

这三条代价换来的是：**改动玩法规则时，可以在 3 秒内知道有没有改坏东西。**

## 二、数据流：单向

```
玩家操作
   │
   ▼
BattleScreen（表现层）
   │  _sim.TryBuildTower(cell, kind) → ActionResult
   ▼
BattleSimulation（逻辑层）
   │  改状态 + 往 _sim.Events 里塞 SimEvent
   ▼
BattleScreen.ConsumeEvents()（同一帧）
   │  按事件类型播音效 / 放特效 / 飘字 / 震屏
   ▼
BoardView.Sync(dt)（每帧）
   │  按"当前状态"重画棋盘
   ▼
屏幕
```

两个关键约定：

**其一，事件不是"状态变更通知"，而是"这一帧发生了什么的流水"。**
模拟层每帧把事件塞进 `Events` 列表，表现层消费完立刻 `ClearEvents()`。
所以表现层不需要理解规则，只需要知道"有个东西在这个坐标死了"。

**其二，棋盘视图不缓存单位，而是每帧按状态重画。**
`BoardView.Sync` 遍历 `_sim.Enemies` 等列表，用 `UiKit.IdPool` 按 **实体 id** 复用图形对象：

```csharp
pool.Begin();
foreach (var enemy in sim.Enemies) {
    Image img = pool.Use(enemy.id);   // 同一个 id 永远拿回同一个 Image
    ...摆位置、换贴图...
}
pool.End();   // 这一帧没出现过的自动回收
```

为什么按 id 而不是按下标复用？因为妖魔中途死亡会让列表顺序变化，
按下标复用会导致"图形对象继承上一个单位的贴图"这类串位问题。

## 三、界面为什么全是代码搭的

工程里**没有任何 `.prefab`**，`Assets/Scenes/Main.unity` 里也只有一个空对象。
所有 Canvas、面板、按钮、滚动列表，都是 `UiKit` 在运行时构造的。

理由：

1. **没有二进制资产引用可以丢失。** 从 git 拉下来打开就能跑，
   不会出现"prefab 丢了引用 / 场景里的 GUID 对不上"这种只在别人机器上复现的事故。
2. **没有 prefab 与代码两份真相。** 卡牌的位置、字号、颜色只在 `BattleScreen.BuildRow` 里定义一次。
3. **动态尺寸更好算。** `GameBootstrap.ComputeCanvasSize()` 在 `Awake` 里就把
   CanvasScaler 缩放后的参考分辨率算出来，于是棋盘格子的边长可以**当帧**确定，
   不用等一帧布局 —— 这样棋盘不会出现第一帧的跳动。

代价是 UI 代码比较长。缓解办法是把重复模式抽成 `UiKit` 的构件：
`NewPanel / NewButton / NewIconButton / NewSlider / NewScroll / NewRow / NewOverlayRoot`，
以及 `Node / Stretch / Place / TopStrip / BottomStrip` 这几个布局原语。

### 字体

Unity 内置字体不含中文字形，直接用会显示成方块。`UiKit.GetFont()` 按
「微软雅黑 → Noto Sans CJK → 源黑 → PingFang → …」的顺序向操作系统要字体
（`Font.CreateDynamicFontFromOSFont`），全都拿不到才退回内置字体。
另外还会 `RequestCharactersInTexture` 预热一批常用汉字，避免开局第一帧卡顿。

### 贴图的三级兜底

`SpriteLibrary.Get()` 依次尝试：

1. `Resources.Load<Sprite>` —— 正常路径
2. `Resources.Load<Texture2D>` → 运行时 `Sprite.Create` —— 贴图导入设置被改成 Default 时
3. 运行时画一个圆角方块 —— 资源整个缺失时

所以**哪怕把 `Assets/Resources/Sprites` 删掉一半，游戏依然能跑**，只是难看。

音频同理：`AudioLibrary` 在找不到音频文件时会现场合成一个正弦提示音。

## 四、配置系统

```
Resources/Config/game_config.json
        │
        │ ConfigLoader.Load（逐字段宽松覆盖）
        ▼
   GameDatabase  ←── DefaultConfig.Build()（代码内置默认值）
```

- **JSON 优先，但永远有兜底。** 字段缺失 → 保留默认值；类型写错 → 忽略并记一条警告；
  JSON 整个解析失败 → 直接用内置默认值。玩家把配置文件改烂了，游戏照样能开。
- **不会和代码脱节。** `game_config.json` 是由代码默认值导出的：

  ```bash
  dotnet run --project tools/CoreTests/CoreTests.csproj export-config Assets/Resources/Config/game_config.json
  ```

  所以字段名永远和代码一致。
- **对战局是复制而不是共享。** `GameBootstrap.NewDatabase()` 每次都返回一份新实例：
  一局里的模拟绝不会改到菜单和典籍正在用的那份配置。

## 五、模拟层内部

`BattleSimulation` 约 1500 行，是唯一一个"大文件"，因为它就是游戏规则本身。
它对外只暴露少量动词，全部返回 `ActionResult`（`ok` + 失败原因枚举）：

```csharp
TryBuildTower(GridPos, TowerKind)     TryUpgradeTower(int towerId)
TrySellTower(int towerId)             TryPlaceTrap(GridPos, TrapKind)
TrySummonSpirit(GridPos, SpiritKind)  CastSkill(SkillKind)
LaunchWave()                          Tick(float dt)
```

调用方（UI）不需要自己判断"灵气够不够 / 格子能不能放"，
拿到 `ActionResult.reason` 直接显示 `ActionResult.Message()` 的中文提示即可 ——
**规则判断只有一处实现**，UI 不可能和规则不一致。

### 每帧的 Tick 顺序

顺序很讲究，因为它决定了"同一帧内谁先动"：

1. 灵气自然回复 + 聚灵阵产出
2. 推进波次计时器 → 到点放妖魔进场
3. 妖魔移动（含减速、狂暴、分裂判定）
4. 妖魔到达山门 → 扣耐久
5. 妖魔攻击射程内的阵法 → 阵法掉血 / 被摧毁 / 幻阵闪避
6. 阵法索敌与开火（含弹道飞行）
7. 仙灵索敌、攻击、修缮山门、寿命倒计时
8. 符箓触发判定
9. 弹道命中结算
10. 清波判定 / 胜负判定

### 统计字段

`TowerKindMask`（五行俱全成就）、`SkillCastCount`、`ThunderCastCount`、`LeakedCount`、
`TotalSpiritEarned/Spent` 这些看起来"像是表现层该统计"的东西，全都放在模拟层里。
理由很简单：**它们必须是确定性的**，而表现层拿不到完整的判定上下文。

## 六、存档与埋点

```
SaveData（Core，纯逻辑，可测试）
   │  ToJson() / FromJson()   ← MiniJson，不是 JsonUtility
   ▼
SaveSystem（Unity，负责落盘）
   │
   ├─→ PlayerPrefs（存档字符串）
   └─→ persistentDataPath/telemetry.jsonl（埋点，JSONL 一行一事件）
```

为什么存档模型放 Core 而不是直接标 `[Serializable]` 用 `JsonUtility`？
因为这样存档的读写可以脱离 Unity 做**往返测试**（写入 → 读出 → 逐字段比对），
存档格式一旦出问题是最难排查的一类 bug，值得为它付一个手写 JSON 解析器的成本。

**埋点**：游戏是纯单机、没有服务器，所以埋点只写成本地 JSONL 文件，
供开发者自己回看"哪一波劝退、哪个阵法没人用"。文件超过 512KB 会整份截断重写，避免无限增长。
埋点内容是：开局难度与 seed、每次建阵/升级、每波结束时的耐久与时间、
以及结算时的胜负/击杀/灵气支出。

## 七、工具链：没有 Unity 也能验证

这是本工程比较特别的一块。因为开发机上没装 Unity，于是做了两条不依赖 Unity 的验证路径：

| 工具 | 作用 |
|---|---|
| `tools/CoreTests` | 用 .NET SDK 编译 Core，跑 146 项断言 + 脚本机器人平衡测试 |
| `tools/UnityCheck` | 把 `Assets/Scripts` 全部代码 + `tools/UnityStubs` 里的 API 桩一起编译 |

`tools/UnityStubs` 里是手写的 UnityEngine / UnityEditor API 桩：**只有签名，方法体是空的**。
它不能替代 Unity（跑不了游戏），但足以查出这些真问题：

- 拼错的成员名（`Mathf.Pingpong`）
- 参数个数不对
- **枚举与整数在 C# 里不能隐式互转**（这是最容易踩的坑）
- 只读属性被赋值
- 方法名与类型名重名导致的解析歧义

这套自检在本工程开发过程中确实抓出过 6 个编译错误 —— 这 6 个错误如果不提前发现，
就要等到用户装上 Unity 打开工程时才会以红色报错的形式出现。

**维护约定**：新增 Unity API 用法时，先在 `tools/UnityStubs` 里补签名，再跑自检。
桩保持"只补游戏真正用到的东西"，所以它始终很小（约 1100 行，含注释）。

## 八、资源生成

`tools/gen_sprites.py`（Pillow）与 `tools/gen_audio.py`（纯 Python）生成全部素材，
详见 README 的「[资源是生成的](../README.md#资源是生成的)」一节。

一个值得记录的实现细节：`gen_sprites.py` 里的 `Art` 类在 **4 倍尺寸**的画布上绘制，
最后统一缩小 —— 这样 Pillow 的线条与圆形会得到抗锯齿的边缘，
而这在移动端小尺寸下是"看起来是否像手绘"的关键。

配色在两个地方必须一致：`tools/gen_sprites.py` 的调色板常量，和
`Assets/Scripts/Unity/Palette.cs`。改配色要同时改这两处（它们是同一套十六进制值）。

## 九、几个刻意的取舍

| 取舍 | 选择了 | 放弃了 | 为什么 |
|---|---|---|---|
| 渲染方式 | uGUI（Canvas 屏空间） | SpriteRenderer + 世界空间相机 | 自适应分辨率不用写额外代码，触摸命中直接复用 uGUI 射线 |
| 界面构建 | 纯代码 | prefab + 场景编辑 | 见上文「界面为什么全是代码搭的」 |
| 逻辑层序列化 | 自写 MiniJson | JsonUtility | 为了能脱离 Unity 测试存档 |
| 配置 | JSON 宽松覆盖 | 强类型 ScriptableObject | 为了不重新编译就能调平衡 |
| 事件协议 | 扁平结构体数组 | C# event / 委托 | 避免每帧产生大量小对象，也避免订阅泄漏 |
| 随机数 | 自带 xorshift32 | UnityEngine.Random | 为了可复现 |
| 音效播放 | 10 个 AudioSource 轮转 | 每次 PlayOneShot | 便于给每个音效单独设音量与音高抖动 |
